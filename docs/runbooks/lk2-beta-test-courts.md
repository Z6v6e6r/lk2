# Два тестовых корта beta ЛК2

Владелец пилота — Games/LK2. Цель — проверить создание бесплатной закрытой игры на двух
существующих кортах «Тестовой станции». Пересмотреть пилот до 2026-10-28 или перед подключением
реального бронирования. Бронь Viva, списание подписки, платежи и изменение расписания Viva
этот сценарий не выполняет. Одновременные локальные игры могут использовать один корт:
создание игры не является резервированием времени.

## Идентичность и доступ

`GAME_TEST_COURT_SCOPE` в `packages/database/src/game-repository.ts` содержит проверенные 2026-09-28 внутренние
PadlHub UUID существующих beta tenant, станции и двух кортов. Соответствия уже присутствуют
в `integration.external_entity_map`; новые ресурсы или альтернативные UUID не создаются.
Классификация ограниченного ресурса использует tenant и конкретный court UUID. Остальные
корты той же станции не получают ограничение автоматически.

`GAMES_TEST_COURTS_ENABLED` по умолчанию выключен; `true` допустим только при `APP_ENV=staging`
и включённых Games commands. Второе обязательное условие — сохранённое право
`games.test-courts` активного пользователя. Роль администратора, JWT со старыми правами и
`BETA_FULL_CLIENT_ACCESS_ENABLED` этого права не заменяют. Проверка читает актуальный профиль
доступа в базе. В исходниках и клиентских настройках списка тестовых аккаунтов нет.

Каталог `GET /user/api/v1/{tenantKey}/games/test-courts` возвращает два внутренних ID и названия
только при полном наборе mappings со статусом `synced` без ошибок и явном доступе.
В остальных случаях — пустой список. Для создания локальной игры источником идентичности
остаётся проверенный реестр внутренних UUID: последующая ошибка provider sync убирает корт
из каталога, но не меняет сохранённую идентичность и не блокирует восстановление попытки
при сохранённом праве доступа. Существование станции и mapping проверяется при новой игре.
Ответ не кэшируется. Создание допускает только точную связку tenant/station/court,
`FRIENDLY`, `PRIVATE`, `NO_PAYMENT`. Join/waitlist проверяют доступ как перед воспроизведением
HTTP-команды, так и при новой записи под блокировкой игры. Отказ пишет в `audit.audit_log`
только внутренние идентификаторы, тип команды, correlation ID и стабильную причину
`GAME_TEST_COURT_ACCESS_DENIED`, без бизнес-записей или нового idempotency результата.
Перевод из листа ожидания повторно проверяет доступ участника под блокировками; при отказе
запись становится `EXPIRED`, запускается проверка следующего участника. Leave/cancel доступны
для очистки.

Публичные список, карточка и рекомендации исключают тестовые корты даже при выключенном
пилоте, включая ранее импортированные PUBLIC-игры. Authenticated game list/detail скрывают
их от пользователей без текущего права. Тестер может открыть приватную игру по ссылке.
Внешние ID Viva в клиентский контракт не входят.

## Подготовка включения

Все операции с runtime и профилями доступа требуют обычной точной авторизации на beta.
Наличие PR, успешных тестов или этого документа не является разрешением выполнить их.

1. Проверить текущий beta tenant, исходные mappings и названия обоих кортов запросами только
   на чтение. При дрейфе остановиться; не переназначать существующие UUID автоматически.
2. Получить явный список тестовых пользователей. Сохранить текущие roles/permissions каждого
   в защищённом операторском контуре, проверить активность и tenant.
3. Подготовить dry-run существующего `npm run user:access:set`. Этот инструмент заменяет
   списки roles/permissions: сохранить все текущие значения и добавить только
   `games.test-courts`. Не применять массовый beta grant для выбора тестеров.
4. Пройти штатный release/deploy с новым API, Worker и Web. До его включения режим остаётся выключенным.
5. После разрешения на конкретные аккаунты применить подготовленные гранты; включить
   `GAMES_TEST_COURTS_ENABLED=true` в `api.env` и `worker.env` через штатную подготовку runtime
   env и deployment. В обоих процессах нужны `APP_ENV=staging` и `GAMES_COMMANDS_ENABLED=true`;
   сохраняются остальные штатные проверки Games config.
6. Проверить tester/ordinary-account пары: каталог 2/0, создание и вход разрешены/отклонены,
   публичная карточка — 404, при выключенном режиме доступ закрыт. Реальное создание тестовой
   игры и очистка требуют отдельно подтверждённого тестового сценария.

## Отключение и восстановление

Выключение флага закрывает новые создания, вход и чтение через каталог/карточки, сохраняя
постоянное исключение из публичных запросов. Для отзыва тестового аккаунта сначала завершить
или отменить его тестовые игры, вывести участника и закрыть его доступ к связанным чатам,
затем убрать точечное право. Чаты, результаты и история имеют собственную модель участия:
снятие этого права само по себе не отзывает уже выданное участие во всех этих подсистемах.

Откат на старый API без правил ограничения снова применит старую видимость импортированных
PUBLIC-игр. После активации использовать выключение флага и совместимый исправленный API;
удаление постоянного списка ограниченных кортов допускается только после проверки всех
связанных игр и импортов. Схема базы и provider state этой поставкой не меняются.
