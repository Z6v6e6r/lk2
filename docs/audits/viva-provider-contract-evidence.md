## Scope and safety constraints

This is a source- and documentation-only audit. It did not authenticate to Viva, call a provider
write, create or change a booking, transaction, payment, refund, capture, callback or webhook,
change flags, deploy, or migrate a shared database. No production/staging credential, merchant ID,
real provider/payment identifier, token or personal data was used or stored.

The integrated system is **Viva CRM at `api.vivacrm.ru`**, not Viva.com/Viva Wallet. Evidence from
the unrelated Viva Wallet product is intentionally excluded. Viva CRM's own operating instruction
states that it can integrate with several acquiring/payment systems. Therefore a generic payment
gateway contract cannot be inferred from the Viva CRM product name.

the available provider evidence.

| Terminal monotonicity           | `CONFIRMED`, `REJECTED` and `MANUAL_REVIEW` cannot transition out. ## Idempotency findings

No official source establishes idempotency for an exact Viva CRM create-booking or
create-transaction/payment operation. Key location, scope, retention, response replay, changed
payload behavior, timeout/reset behavior and production/demo parity are all unproven. Finding the
word "transaction" or "webhook" on the product page does not change this result. A second provider
POST remains forbidden after an ambiguous transport outcome.

## Read-back and provider-status mapping

There is no provider-valid positive status mapping yet. Only these conservative mappings are safe:

| Viva observation                                                        | Internal classification                  | Internal transition                    | Allowed side effects                                                          |
| ----------------------------------------------------------------------- | ---------------------------------------- | -------------------------------------- | ----------------------------------------------------------------------------- |
| Unauthenticated/unverified callback                                     | `UNAVAILABLE` / ignore as provider truth | Keep current state                     | Audit/metric only; no payment, seat or retry mutation                         |
| Read path unavailable or unversioned                                    | `UNAVAILABLE`                            | `UNKNOWN` then bounded `MANUAL_REVIEW` | Schedule bounded read-back only after a valid read adapter exists             |

| Status without exact merchant/reference/amount/currency binding         | `MISMATCH` or `AMBIGUOUS`                | `UNKNOWN` then bounded `MANUAL_REVIEW` | No confirm/reject side effects                                                |

## Amount and currency assessment

Official reports describe ruble-denominated UI columns, discount/deposit formulas, per-booking rows
and paid/refund history. They also prove that one transaction may contain multiple positions, that a
payment action can fund only a subset of a long booking, and that partial refunds exist. This makes a
simple transaction-total comparison unsafe. The reports do not define API amount type/minor units,
rounding, currency code, source of truth, authorization/capture/settlement fields, fees/net/tips,
reversal/chargeback, stable allocation IDs, or immutable merchant/reference binding. The older
official product instruction also advertises multi-currency capability through one integrated
gateway, so ruble-labeled reports cannot prove a universal RUB contract. A Viva UI/report/widget
status therefore cannot confirm the native Games reservation.

## Contradictions and unresolved questions

No two accessible official sources directly contradict each other. There are material scope
tensions: reports are RUB-labeled while an older product instruction advertises multi-currency;
three public status vocabularies cover report rows, widget analytics and product UI; and current
partial refunds postdate the older product instruction. Because these sources describe different
surfaces rather than one versioned API field, the result is `PARTIAL/UNPROVEN`, not a fabricated
`CONTRADICTED`. The decisive freshness/access gap remains: the versioned API contract is protected
or absent.
