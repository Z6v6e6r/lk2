# R1 API/Worker update after ledger119

This is the fixed R1 extension of the existing `--critical-api-worker` controller, not a new deployment route. The owner-authorized package must bind source CI, one canonical V2 publication, exact target, retained API/Worker702, Web871, Realtime702, database identity, runtime secret hashes, and existing Android gate snapshot. All new R1 command and notification activation flags remain off. This step alone is not functional phone acceptance.

## Required custody

Freeze one final source for enrollment, closed migrations and this rollout. Keep the exact canonical `r1-tail108-119-migration.json`, final attempt request/capsule/plan/receipt/success/cleanup/role proof, backup receipt/preimage, and both stopped final attempt containers. The backup attestor remains coupled to that enrolled source and canonical request; do not replace them during rollout or recovery. Historical completion is checked independently of current API/Worker identities. Fresh preflight separately validates current119 catalog/security and stopped executors.

Select the installed mixed descriptor using the retained Web871 release ID. Independently bind all four installed application image digests and the current secret set. Do not reconstruct a baseline from the older API702 directory. Preserve the existing released Worker gate and its override for rollback.

## Transition

1. Validate source/publication, completed119 evidence, target, current catalog and privilege preimage, existing parent capabilities through both actual application connections, secrets, retained services, and provider gates. Seal operation and plan in the existing capsule before effects.
2. Prepare the candidate Worker delivery gate as HELD; pull/smoke the immutable API and Worker images.
3. Stop old Worker, verify no sending work remains, then stop old API. Existing runtime command flags and identity linking must be off in both sealed files and actual containers.
4. Apply only the source-reconstructed18-relation grant transaction, with preimage/postimage compare-and-swap, fixed role, bounded statement/lock timeout and a final expiry check. No parent grants, schema creation, role creation, default ACL changes or supplied SQL are accepted.
5. Preserve secrets; start candidate API, then Worker under HELD gate. Verify actual application role privileges, exact post-grant semantic catalog, retained Web/Realtime, private/public readiness, and the existing observation policy. Bind grant intent and successful child-exit proof into installed evidence.
6. Install descriptor; release the candidate delivery gate only after observation and final attestations. Verify the resulting receipt and installed baseline. This preserves existing Android delivery; it does not activate new campaigns or prove device delivery.

## Failure and recovery

Before delivery release intent, recovery contains both applications and verifies database/grant evidence before restoring old images. It restores and verifies the old Worker gate mount, environment and Compose hash. Application rollback retains ledger119 and the reviewed compatible grants; it does not reverse migrations or ACLs.

A grant intent without a proven successful original `psql` child exit is **UNKNOWN**, even when a read currently resembles the preimage or postimage. Never replay the grant transaction or infer terminality from elapsed time. Keep both apps contained; independently establish original execution terminality and the exact database state before preparing a separate recovery. The pure inverse ACL transaction exists for an explicitly scoped recovery after dependent consumers are contained; the application rollback never invokes it automatically.

At or after delivery release intent, provider calls may have begun. Reconcile the candidate and its gate; do not restart the old sender automatically.

APK installation and device push/offline recovery remain DEVICE evidence collected on the owner's phone. No CI or rollout receipt substitutes for those results.

### Temporary migrator schema access during runtime grants

Runtime grant plans use `PHUB_R1_RUNTIME_GRANTS119_V2`. A new capture includes the actual
owner (required to equal the fixed `phub_beta` schema-owner contract), complete non-null raw ACL and effective migrator USAGE/CREATE for every fixed grant
schema. V1 captures/plans are not accepted; regenerate the plan from a fresh canonical
`R1_RUNTIME_GRANT_CATALOG_SQL` capture. Outer operation identity is unchanged, but the new
plan hash must be sealed and reviewed; never reuse an old grant intent or terminal receipt.

Apply and recover both start as the database administrator, lock the fixed relations and
validate the whole preimage. Only missing schema USAGE is temporarily granted as the fixed
`phub_beta` schema owner. Table/column grants still execute under `SET LOCAL ROLE phub_migrator`, preserving
their grantor identity. The transaction then revokes only its added USAGE as the same schema
owner and verifies the full final snapshot, including exact original schema ACLs. Existing
USAGE/CREATE and unrelated grants are retained. No schema CREATE is added. Null schema ACLs
are refused rather than materialized. Any drift/error rolls back the entire transaction;
ambiguous execution still follows the existing no-replay/terminal-proof contract.
