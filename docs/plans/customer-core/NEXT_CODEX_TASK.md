# Следующее задание: КЯ-01a — контакт отдельно от входа

Статус: **Proposed prompt**. Это текст будущего задания; КЯ-00 не разрешает его исполнять.

> Работай в `Z6v6e6r/lk2` по актуальным `AGENTS.md` и отдельному чистому task worktree. Сначала прочитай `docs/plans/customer-core/{AUDIT,ARCHITECTURE,ROADMAP,MIGRATION_AND_ACCEPTANCE}.md`, ADR 0001/0002/0004 и фактическую миграцию `packages/database/migrations/0091_verified_phone_uniqueness.sql`. Проверь свежий `origin/main`, PR и миграционную цепочку. Не считай документационный проект принятым runtime-контрактом; если он противоречит текущему schema head, покажи конфликт до кода.
>
> **Один результат:** tenant-scoped storage и repository для контактного телефона/email клиента, допускающий один нормализованный контакт у нескольких `identity.users.id` в одном tenant, без выдачи login права. Существующий UUID, verified phone claim в `profile.user_summaries.phone_e164` и normal login по `(issuer,subject)`/provider profile ID сохраняются. Контакт не связывает пользователей автоматически.
>
> **Разрешённые пути:** новая expand-only SQL migration в `packages/database/migrations/`; узкий repository и тесты в `packages/database/src/`; при необходимости export из `packages/database/src/index.ts`; соответствующая правка `docs/plans/customer-core/ARCHITECTURE.md` при обнаруженной корректировке модели. **Запрещённые пути:** `apps/**`, `packages/auth/**`, `packages/viva-adapter/**`, `contracts/openapi/**`, SDK, ph-admin, lk, root config/dependencies/CI/deploy/AGENTS. Не трогай индекс 0091 и не меняй текущий вход, флаги, Viva routing или live/shared БД.
>
> **Модель:** FK `(tenant_id,user_id)` на `identity.users`; normalized value и type, provenance, `verified_at` отдельно по телефону/email, optimistic version, created/updated/changed actor/correlation. Unique только внутри `(tenant_id,user_id,type,normalized_value)`; индекс поиска по `(tenant_id,type,normalized_value)` не уникален. Операция записи через tenant transaction, CAS, idempotency/audit (либо точное объяснение, почему в первом increment запись недоступна снаружи). Raw contact никогда не в audit payload. RLS `FORCE` и миграция expand-only.
>
> **Точные проверки на синтетических данных:** (1) один телефон у двух UUID в одном tenant сохраняется только как contact; (2) повтор одного user/contact не создаёт дубль; (3) тот же phone в другом tenant не виден; (4) чужой tenant/user FK и RLS запрещают доступ; (5) `verified_at` нельзя получить из import без proof; (6) older source version не перезаписывает локально подтверждённое поле; (7) конфликт optimistic version и concurrent insert возвращают стабильный результат; (8) уникальный verified claim 0091 и mapping `(issuer,subject)`/provider profile ID продолжают разрешаться в прежний UUID, конфликт fail closed; (9) общий contact не участвует в login/link/recovery; (10) apply/reapply на полностью disposable PostgreSQL и rollback/forward plan. Запусти scoped tests, затем `npm run check` из-за schema/RLS. Независимый security + migration review до task-branch push.
>
> **Полномочия:** scoped implementation, local checks, commit, push только своей ветки, Draft PR и чтение CI разрешены действующими правилами. Никаких real/shared migrations, provider writes, merge/deploy, secret/ACL changes на живой цели. Не устанавливай зависимости без необходимости. При отсутствующем disposable PG выполни остальные независимые проверки и честно отметь непроверенное.
>
> **Готово, когда:** PR содержит только этот слой, UUID прежний, общий контакт не создаёт login binding, перечисленные tests и review представлены с фактическими результатами, а downstream КЯ-01b (перевод auth lookup и contract) явно остаётся отдельной задачей.
