# Общий контракт CREATE ↔ JOIN для коммерческого создания игры

Статус: согласование (проект). Документ фиксирует минимальную общую границу между
контуром CREATE (эта задача) и контуром JOIN (параллельная задача), чтобы обе стороны
могли разрабатываться независимо и сойтись без второго checkout, второго механизма
отмены и второй модели идентичности.

Границы доказательств: **SOURCE**. Ни LK1, ни Viva, ни стенд не проверялись; где статус
неизвестен, это написано прямо.

## 1. Владение и порядок изменений

| Артефакт                                                                                                                                                                                        | Автор                             | Второй участник | Правило                                                           |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- | --------------- | ----------------------------------------------------------------- |
| Схемы CREATE: `QuarterCreateInput`, `GetQuarterCreateCapability`, `CreateGameOperation`, котировка/согласие                                                                                     | CREATE                            | JOIN (ревью)    | Меняет только автор CREATE, одним PR                              |
| Схемы JOIN: `JoinConditions`, `JoinGameRequest`, `JoinOperation`, `join-conditions`                                                                                                             | JOIN                              | CREATE (ревью)  | Меняет только автор JOIN                                          |
| Общие файлы: `contracts/openapi/user/v1/games.yaml`, `packages/api-contracts/src/generated-user.ts`, `packages/api-sdk/src/**`, `docs/contracts/game-join-conditions.md` (секция длительностей) | CREATE генерирует, JOIN согласует | —               | Общий файл правится одним PR; порядок мержа указывается в теле PR |
| `docs/contracts/game-commercial-create.md`                                                                                                                                                      | CREATE                            | JOIN            | Владелец — CREATE                                                 |
| `docs/contracts/game-join-conditions.md`                                                                                                                                                        | JOIN                              | CREATE          | Владелец — JOIN                                                   |

Правило одного автора действует на уровне схемы, а не на уровне строки: правка
чужой схемы — это предложение в PR владельца, не самостоятельный PR.

Версия контракта: **v1 расширяется аддитивно** (новые необязательные поля, новые
значения перечислений, новые `nextAction`). Несовместимых изменений в v2 нет; v2 не
трогаем. Клиент, не знающий расширения, продолжает работать на прежнем подмножестве.

## 2. Идентичность коммерческой цели

- `draftGameId` и `operationId` детерминированы из проверенных claims и ключа;
  повтор с тем же ключом называет ту же цель.
- Для новых попыток идентичность привязывается к типу операции и цели:
  домен вида `game-create-operation:v2\0CREATE_GAME\0<tenant>\0<user>\0<key>`.
  Общий домен `booked-operation-admission:v1` (используется JOIN) остаётся только для
  чтения исторических попыток.
- Совместимость восстановления: сохранённый `operationId` читается как есть, reconcile
  принимает идентификатор, производный по прежнему домену, для записей, созданных до
  перехода. Идентификаторы существующих попыток **не пересчитываются**.
- Ограничение локального fence: `games.command_idempotency` ключуется
  (tenant, principal, key) и отклоняет вторую команду с тем же ключом
  (`409 GAME_QUARTER_CREATE_KEY_CONFLICT`). Поэтому до отдельной expand/contract
  миграции действует клиентское правило: **один ключ — одна операция**, ключ не
  переиспользуется между CREATE и JOIN.

## 3. Серверная котировка и срок действия

Источник цены — только владелец (LK1/CUP/Viva). LK2 не вычисляет скидки, покрытые
минуты, льготы и итог; он передаёт ответ как есть и показывает его.

Обязательные поля котировки:

```text
quoteId, operationId, basis (SUBSCRIPTION | OWN_QUARTER | WHOLE_COURT),
durationMinutes (60|90|120), startsAt, endsAt,
amountMinor, currency, coveredMinutes, surchargeMinor,
expiresAt, policyVersion, priceDigest
```

- Котировка адресуется черновику: `target.kind=DRAFT_GAME`, `target.id=draftGameId`,
  `expectedRevision=1` (для существующей игры JOIN использует `target.kind=GAME`,
  как в `POST /lk/subscriptions/game-price-preview`).
- Срок действия — свойство владельца (предложение: 120–300 с). Истечение котировки
  означает «получить новую», а не «повторить оплату».
- Никакие клиентские поля (цена, способ оплаты, скидка) в котировку не принимаются.

## 4. Точная сумма согласия

Согласие пользователя — это ровно `{quoteId, amountMinor, currency, expiresAt}`,
подтверждённые до создания. Сервер сверяет эхо с действующей котировкой и отклоняет
без создания операции (`GAME_PRICE_CONFIRMATION_REQUIRED`). Изменение суммы = новая
котировка = новое согласие; старое согласие не «доплачивается» молча.

Сумма, списанная владельцем в квитанции, должна совпадать с согласованной; расхождение —
не успех и не повод повторять списание, а `UNKNOWN` + сверка у владельца.

## 5. Состояние оплаты и допустимое следующее действие

```text
paymentState: QUOTE_REQUIRED | AWAITING_CONSENT | PENDING_PROVIDER |
              AWAITING_BOOKING | CONFIRMED | REFUSED | UNKNOWN |
              CANCELLED_PENDING | REFUND_PENDING
nextAction:   CONFIRM_PRICE | PAY | WAIT | RECONCILE | JOIN_ENABLED | CONTACT_SUPPORT
```

- `UNKNOWN` не означает `FAILED` и не означает «списания не было».
- Истечение клиентского окна оплаты само по себе не освобождает место и не завершает
  операцию: сначала читается фактический исход у владельца.
- Разрешённые переходы и запреты (нельзя из `UNKNOWN` в `REFUSED` без ответа владельца,
  нельзя из `CONFIRMED` в `CANCELLED_PENDING` и т. п.) фиксируются сервером; клиент их
  только отображает.

## 6. Подтверждение бронирования и исполнения подписки

Единственный источник успеха — квитанция владельца:

```text
receiptId, confirmedAt, bookingRef, usageRef, appliedRule,
priceCharged { amountMinor, currency }, provider: VIVA
```

Публичная проекция отдаёт только `{provider, status, confirmedAt, bookingRef?}` без
внутренних идентификаторов и сумм, если владелец не разрешил иное. Возврат с платёжной
страницы, HTTP 200 владельца и наличие `bookingRef` без квитанции успехом не считаются.

## 7. Отмена ожидающей оплаты ≠ отмена подтверждённого участия

| Сценарий                             | Основание                                       | Механизм                                                           | Возврат                                  |
| ------------------------------------ | ----------------------------------------------- | ------------------------------------------------------------------ | ---------------------------------------- |
| Ожидающая оплата (деньги не списаны) | `AWAITING_CONSENT`/`PENDING_PROVIDER`/`UNKNOWN` | `release` у владельца по `operationId` (идемпотентно), повторяемый | нет                                      |
| Подтверждённое участие               | `CONFIRMED`                                     | существующие правила отмены игры/участия                           | по политике владельца, отдельный процесс |

Второй механизм отмены не создаётся: LK2 использует owner `release`/`compensate` из
`docs/contracts/game-commercial-create.md` и существующие правила отмены участия.

## 8. Восстановление после неизвестного исхода

- Повтор с тем же ключом и телом возвращает ту же операцию (`replayed=true`), не создавая
  вторую финансовую попытку.
- Перезапуск приложения, обновление страницы, возврат с платёжной страницы и повторное
  нажатие не создают новую попытку.
- Восстановление: `GET` операции + явный `reconcile` тем же ключом и телом; только чтение
  статуса/квитанции у владельца.

## 9. Данные, по которым созданная игра становится доступной для JOIN

CREATE обязан выдать (после подтверждённого коммерческого исполнения и бронирования):

```text
gameId, revision, lifecycleState, visibility,
startsAt, endsAt, durationMinutes (60|90|120), joinCutoffAt,
capacity, occupiedSeats, freeSeats,
paymentMode, wholeCourtPaid (bool),
levelRange {from,to}|null,
priceForDisplay {amountMinor,currency,basis,quoteId} | null,
joinEligible (bool)
```

- `wholeCourtPaid=true` означает, что все места уже оплачены организатором; JOIN не
  требует с участника оплаты и не создаёт платёжную попытку.
- Пока `lifecycleState` не `SCHEDULED` или проекция не готова, игра не публикуется и не
  предлагает запись. LK2 не обещает JOIN, который невозможен.
- Доступность, цена и льготы участника остаются за JOIN/владельцем; CREATE передаёт
  только факты игры, а не решение о праве на запись.

**Известное расхождение, требующее изменения на стороне JOIN:** текущий контракт
`docs/contracts/game-join-conditions.md` явно допускает длительности 60 или 90 минут и
режимы `SPLIT`/`SUBSCRIPTION` при 4 местах. Согласованный объём CREATE добавляет
120 минут и полностью оплаченный корт (`wholeCourtPaid`). Пока JOIN не расширен,
создание на 120 минут или с оплатой всего корта не может быть принято как готовое
к записи; это общий пункт приёмки, а не дефект одной стороны.

## 10. Переиспользование существующих механизмов

- **#431 в этом репозитории** — merged `fix(migration): canonicalize the container mount
order in fingerprints` (PR #431, merge `2026-10-20`), к checkout/оплате/отмене
  отношения не имеет. Механизма оплаты в #431 нет и не готовится.
- **Checkout.** В LK2 есть только локальная песочница подарочных сертификатов
  (`/gift-certificate-payment-sandbox/{paymentId}` + `sandbox-confirm`, документ
  `docs/domains/gift-certificates.md`), реального провайдера она не вызывает. Реальный
  checkout остаётся у LK1 (`docs/domains/monthly-subscription-purchase.md:3` — «Existing
  LK1 checkout remains the owner-compatible legacy consumer»). Второй checkout в LK2 не
  создаётся.
- **Чтение коммерческой операции.** `GET /booked-operations/{operationId}` (LK1 owner read,
  `docs/contracts/booked-operation-read.md`) — используется как есть.
- **Котировка для существующей игры.** `POST /lk/subscriptions/game-price-preview` —
  образец полей для CREATE-котировки по черновику; новых эндпоинтов «на всякий случай»
  не добавляем.
- **Освобождение места.** `game.reservation.expire.v1` объявлен, но исполнителя нет; для
  CREATE освобождение возможно только по ответу владельца, не по локальному таймеру.

## 11. Стоп-условия

Стороны не начинают реализацию, пока не согласованы: имена полей котировки и квитанции,
набор состояний оплаты и `nextAction`, форма `target` для черновика, правило
`wholeCourtPaid`, и порядок мержа общих файлов. Любое из этих изменений после старта —
отдельный PR автора схемы.
