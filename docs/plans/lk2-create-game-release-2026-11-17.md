# LK2 CREATE GAME: выбранный релизный путь и план последовательных PR

Дата: 2026-11-17.

Основание: аудит LK2 CREATE GAME (`docs/audits/lk2-create-game-2026-11-17.md`, едет в PR #669),
согласованный продуктовый объём (60/90/120 минут; варианты A/B/C) и
[общий контракт CREATE ↔ JOIN](../contracts/game-create-join-shared-contract.md).

Границы доказательств: **SOURCE** и **LOCAL**. Живой LK1/Viva, стенд и деплой не затрагивались.

## 1. Выбранный путь: расширение `/game-create-operations` (v1, аддитивно)

Основа — существующий подтверждаемый owner-путь. Проверка расширяемости:

| Свойство текущего пути | Факт                                                                                                          | Следствие для расширения                                                                                                                                                                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Публичный вход         | 4 поля, строгая проверка набора ключей (`packages/domain/src/quarter-create.ts:62-82`)                        | Новые параметры добавляются как **необязательные** поля с версией контракта; старый запрос остаётся валидным                                                                                                                                              |
| Версия контракта       | `contractVersion: 1` в запросе/капсуле/результате                                                             | Расширение = `contractVersion: 2` (или capability-флаг), а не изменение семантики v1                                                                                                                                                                      |
| Журнал                 | `games.quarter_create_attempts.request jsonb` (до 8192 байт), `admission jsonb`                               | Новые поля сохраняются без миграции колонок                                                                                                                                                                                                               |
| Уникальность попытки   | `unique (tenant_id, actor_user_id, court_id, starts_at)` (`0110:32-33`)                                       | **Длительность входит в ключ?** Нет. 60 и 120 минут на одном корте/времени у одного организатора конфликтуют → нужно решение: добавить `duration_minutes` в индекс (expand-миграция) либо зафиксировать правило «одна попытка на организатора/корт/время» |

| Публичный результат    | `request/operation/gameProjection/registration/reason`                                                        | Котировка и состояние оплаты добавляются как вложенные объекты                                                                                                                                                                                            |

**Вывод:** путь расширяем без нарушения действующих операций, при трёх условиях: (1) владелец
v2 в LK1, (2) решение по индексу уникальности при разных длительностях, (3) аддитивные поля с
соблюдением общего контракта. Пока владелец v2 не готов, LK2 обязан **отказывать** на
расширенные параметры стабильным кодом, а не молча их игнорировать.

## 2. Судьба advisory WARN

Решение: **вывести из эксплуатации**, не поддерживать два коммерческих процесса.

Основания:

- Контур не бронирует, не списывает и не выдаёт квитанцию (`SKIPPED_ADVISORY`).
- Оплаченная игра в нём навсегда остаётся `PROVISIONING`: `immediateSchedule = paymentMode === 'NO_PAYMENT'`
  (`packages/database/src/game-repository.ts:964`), список и карточка требуют `SCHEDULED`
  (`:1494`, `:1667`, `:1811-1813`), потребителя `game.provisioning.advance.v1` нет.
- Полоса выкладки допускает только `QUARTER_OWNER` (`scripts/timeweb-commercial-runtime-contract.js:64-68`),
  то есть WARN нельзя включить на стенде штатным путём.
- Пользовательский вход `?commercialCreate=1` ведёт в тупик и конкурирует с рабочим подписочным путём.

Порядок вывода (после появления подписочного входа через capability):

1. Убрать платные режимы и URL-гейт из Web, заменив их серверным capability и явным входом
   «Игра по подписке».
2. Удалить advisory-транспорт и ветку `POST /games` для платных режимов; серверный ответ для
   платного `POST /games` остаётся `409 GAME_PAYMENT_REQUIRED`.
3. **Не добавлять** потребитель `game.provisioning.advance.v1`: сначала доказать, что выбранному
   релизному пути он нужен. Квартальному пути он не нужен — публикация идёт через импортёр LK1.

Срок: отдельный небольшой PR после контракта с LK1 (см. §8), чтобы не удалять код, который ещё
переиспользуется в тестах.

## 3. Версия расширения контракта

- **Публичный API:** расширение идёт как `contractVersion: 2` в существующем семействе
  `contracts/openapi/user/v1` (аддитивные необязательные поля + новые значения `nextAction`).
  Запросы `contractVersion: 1` принимаются без изменений; `GET /capability` объявляет
  `createContractVersions: [1, 2]`. Семейство `user/v2` не меняется вовсе.
- **Wire владельца:** капсула `schemaVersion: 2` с `durationMinutes`, `terms` и денежными
  базисами; капсулы `schemaVersion: 1` продолжают читаться для уже подтверждённых операций.
- **Совместимость клиентов:** старый Web/Android/iOS (4 поля, `contractVersion: 1`) продолжает
  работать; расширенные поля отправляет только клиент, увидевший версию 2 в capability.
- **Совместимость серверов:** LK2 отправляет владельцу v2 только при явном подтверждении
  поддержки; иначе стабильный отказ `GAME_CREATE_TERMS_UNSUPPORTED`, без скрытого игнорирования.

## 3a. Идентичность и совместимость

- `operationId`/`draftGameId` для **новых** попыток привязываются к действию и цели
  (`game-create-operation:v2`), чтобы CREATE и JOIN не делили идентичность.
- Существующие попытки читаются по сохранённым id; reconciliation принимает прежний производный id.
  Пересчёта идентификаторов нет.
- Локальный fence `games.command_idempotency` пока ключуется (tenant, principal, key), поэтому
  один ключ = одна операция. Клиентское правило: отдельный ключ на каждое действие и цель.
  Расширение ключа fence (action+target) — только если появится реальная потребность; это
  expand/contract миграция, не часть первого релиза.

## 4. Пользовательский процесс (три шага)

**Шаг 1 — место и время.** Станция, дата, время, корт, длительность 60/90/120. Доступность и цена
проверяются сервером (котировка владельца), клиент не считает сам.

**Шаг 2 — параметры игры.** Название (1–160 символов после trim), диапазон уровней (пара, от ≤ до,
канонические коды), открытая/приватная. Сервер валидирует и передаёт владельцу как применяемые
факты; при отсутствии поддержки — стабильный отказ, без скрытого игнорирования.

**Шаг 3 — стоимость и создание.** Серверная котировка (`amountMinor`, `currency`, `coveredMinutes`,
`surchargeMinor`, `expiresAt`, `basis`), выбор варианта A/B/C, подтверждение точной суммы
(`quoteId + amountMinor + currency + expiresAt`), создание. Кнопка блокируется на время операции;
повторное нажатие, перезапуск и возврат с платёжной страницы не создают новую попытку.

**Публикация и JOIN.** Игра становится видимой и доступной для записи только после квитанции
владельца (для подписки — подтверждённое использование льготы + доплата, если требуется) и
готовой проекции. До этого — понятное ожидание, без предложения повторной оплаты.

## 5. Варианты оплаты и серверная власть

| Вариант                                  | Что платит организатор                  | Что обязан подтвердить владелец               | Что получает JOIN                    |
| ---------------------------------------- | --------------------------------------- | --------------------------------------------- | ------------------------------------ |
| A. Своя четверть деньгами                | ровно `amountMinor` за свою четверть    | платёж + бронь всего корта                    | участники платят по правилам JOIN    |
| B. Своя четверть по подписке (+ доплата) | `surchargeMinor`, если политика требует | использование льготы + доплата + бронь        | участники платят по правилам JOIN    |
| C. Весь корт деньгами                    | полная стоимость корта                  | платёж + бронь + пометка «все места оплачены» | **оплата с участников не требуется** |

Правила:

- ЛК2 не воспроизводит коммерческие правила: покрытые минуты, льгота и доплата — только из
  ответа владельца. 60 минут не считаются автоматически бесплатными.
- Подписка для оплаты всего корта не реализуется.
- `wholeCourtPaid` проверяется сервером JOIN; клиент не решает, платить ли участнику.

## 6. Матрица 60/90/120 × A/B/C

Каждая ячейка — отдельный приёмочный случай. «Котировка» = обязательные поля владельца,
«Квитанция» = подтверждение брони, «Публикация» = появление карточки, «JOIN» = поведение записи.

| #   | Длительность | Вариант | Котировка (ожидается)                                         | Квитанция                          | Публикация              | JOIN                                       |
| --- | ------------ | ------- | ------------------------------------------------------------- | ---------------------------------- | ----------------------- | ------------------------------------------ |
| 1   | 60           | A       | `basis=OWN_QUARTER`, цена своей четверти, `coveredMinutes=0`  | платёж + бронь                     | SCHEDULED после receipt | платит по правилам                         |
| 2   | 90           | A       | то же, длительность 90                                        | платёж + бронь                     | SCHEDULED               | платит по правилам                         |
| 3   | 120          | A       | то же, длительность 120                                       | платёж + бронь                     | SCHEDULED               | платит по правилам (после расширения JOIN) |
| 4   | 60           | B       | `coveredMinutes` по политике; `surchargeMinor` (может быть 0) | льгота + доплата (если >0) + бронь | SCHEDULED               | платит по правилам                         |
| 5   | 90           | B       | то же                                                         | то же                              | SCHEDULED               | платит по правилам                         |
| 6   | 120          | B       | то же; политика может потребовать доплату                     | то же                              | SCHEDULED               | платит по правилам (после расширения)      |
| 7   | 60           | C       | `basis=WHOLE_COURT`, полная цена корта                        | платёж + бронь                     | SCHEDULED               | **оплата не требуется**                    |
| 8   | 90           | C       | то же                                                         | то же                              | SCHEDULED               | **оплата не требуется**                    |
| 9   | 120          | C       | то же                                                         | то же                              | SCHEDULED               | **оплата не требуется** (после расширения) |

Обязательные негативные случаи к матрице:

- цена изменилась между котировкой и согласием → `GAME_PRICE_CONFIRMATION_REQUIRED`, попытка не создана;
- котировка истекла → новая котировка, не повторная оплата;
- отказ платежа → терминальный отказ, возврат не требуется (деньги не списаны);
- тайм-аут владельца → `UNKNOWN`, тот же ключ на reconcile, никакой новой финансовой попытки;
- потеря ответа после успешной брони → восстановление по квитанции, без второго списания;
- повторное нажатие/перезапуск/возврат с платёжной страницы → без новой попытки;
- истечение окна оплаты при отправленной команде → место не освобождается локально;
- отмена ожидающей оплаты ≠ отмена подтверждённого участия;
- недоступный корт → стабильный отказ, без брони и без списания.

## 9. Внешние действия для приёмки (каждое — отдельное разрешение)

1. Установить владельца quarter CREATE v2 в LK1 по процедуре репозитория `lk`.
2. Сгенерировать ключ делегации на LK2 и внести публичный ключ в LK1 (один доверенный ключ;
   замена отрезает другие контуры).
3. Записать ключи и флаг `GAME_COMMERCIAL_CREATE_ENABLED=true` + `QUARTER_OWNER` в `api.env`.
4. Опубликовать и продвинуть сборку на стенд.
5. Read-only приёмка: capability, корты, подписки, котировки для 60/90/120 и A/B/C без записи.
6. По одному реальному CREATE на согласованные ячейки (начиная с 90/A, 120/B, 60/C), затем JOIN
   на игру с оплаченным кортом для проверки отсутствия повторной оплаты.
7. Собрать доказательства: запрос/ответ (без токенов), квитанция, карточка, состав, JOIN,
   операторский запрос по «зависшим» попыткам.

## 11. Чего в этом плане нет

- второго checkout и второго механизма отмены (переиспользуются LK1 checkout, owner `release`,
  существующие правила отмены);
- подписки для оплаты всего корта;
- потребителя `game.provisioning.advance.v1` «потому что команда есть»;
- несовместимых изменений v2;
- локального расчёта скидок, минут и итоговой суммы.
