# Мобильный вход: Яндекс ID и подготовка собственного метода

Статус: предложение следующего этапа, 2026-10-02. Это контракт подготовки, не реализованные
API, схема БД или включённый LOCAL provider.

## Текущий продуктовый порядок

Основной вход в подключённой Android-сборке — Яндекс ID через существующий VIVA OAuth.
СМС — явная вторичная альтернатива. Выбор экрана не отправляет запрос авторизации; нужны
действие клиента и действующие согласия. Механизм OAuth, PKCE, callback, native session,
refresh/logout и provider binding в этом изменении не меняются.

Android открывает системный браузер через `ACTION_VIEW`; перевод запуска в Custom Tabs —
отдельный следующий шаг. iOS сейчас использует OTP; Яндекс нельзя показывать рабочим до
реализации ASWebAuthenticationSession, проверенного возврата, одноразового native handoff
и восстановления после закрытия процесса. Нельзя переиспользовать Android callback под iOS.

Собственный вход после подготовки: клиент подтверждает номер телефона, указывает почту и
пароль, подтверждает почту. В дальнейшем входит по почте и паролю без СМС при каждом входе.
Почта до подтверждения — только pending значение, не login/recovery identifier.

## Один пользователь и несколько методов

Стабильный ключ — существующий `identity.users.id` (PadlHub UUID). Выбор входа не выбирает
источник расписания, платежей или абонементов. Существующие Viva `(issuer, subject)` и
provider mappings сохраняются. Контакт, даже подтверждённый, сам по себе не разрешает вход.

- Для уже вошедшего пользователя LOCAL enrollment добавляет метод к UUID из проверенной
  consumer-сессии. Перед изменением требуется свежая повторная авторизация уже привязанным
  методом (сейчас Яндекс/VIVA), затем подтверждение нового телефона и почты. Только активной
  сессии и нового номера недостаточно. `userId` из тела запроса не определяет целевой UUID.
- Первый собственный increment ограничен enrollment уже вошедшего пользователя и не создаёт
  новый UUID. Самостоятельная регистрация нового пользователя отложена до отдельной
  admission/reconciliation policy: Yandex-профиль без login phone/email нельзя отличить от
  нового человека только по новым введённым контактам. Неоднозначность направляется в
  recovery/quarantine без создания пользователя и без автоматического слияния.
- Если телефон, email login или внешний subject уже связан с другим UUID, enrollment
  завершается конфликтом и отдельным восстановлением/подтверждённой привязкой. Совпадение
  имени, контактной почты или номера не объединяет пользователей автоматически.
- Яндекс и СМС уже доступны через VIVA, но совпадение UUID одного человека должно быть
  доказано отдельной PROVIDER/STAGING проверкой. Наличие обоих экранов такого доказательства
  не даёт. Для различных subjects требуется явный link flow, а не слияние по телефону.

## Подтверждение и хранение

Phone/email challenges выдаёт доверенный backend verifier. Каждая попытка привязана к tenant,
целевому user/session family, purpose, нормализованному
значению, версии и команде. Обязательны короткий TTL, ограничение попыток, одноразовое
потребление, `Idempotency-Key`, `X-Correlation-ID`, CAS и редактированный audit.
Доказательство контакта нельзя использовать для другой цели, пользователя или tenant.
Recent old-factor reauth — отдельное одноразовое серверное доказательство с той же привязкой
к actor/session/command/TTL; возраст сессии или JWT iat сам по себе его не заменяет.

Сервер нормализует российский телефон в E.164. Для email следующему этапу нужно зафиксировать
правило сравнения local part/domain, IDN и повторного подтверждения; нельзя произвольно
удалять точки или `+suffix`. Уникальность требуется для активных login identifiers внутри
tenant. Общие контакты могут повторяться и не должны становиться account lookup.

Планируемые `identity.login_methods` и `identity.password_credentials` принадлежат Identity.
Профильные контакты и существующий verified phone claim миграции `0091` сохраняют свои
контракты; их нельзя превратить во второй writer login binding. Схема — expand/migrate/contract,
номер будущей миграции определяется по актуальному head. PR клиентского ядра #340 и
подтверждения телефона #244 — отдельные незавершённые работы, не реализованные зависимости.

Пароль хранится только как Argon2id PHC hash с уникальной случайной солью и версионированными
параметрами; библиотека и параметры выбираются после проверки зависимостей и benchmark.
Если используется pepper, его версия хранится в записи, секрет — вне БД. Пароль, hash,
OTP и proof tokens не возвращаются в API, не пишутся в audit/logs и не сохраняются клиентом.
Клиент допускает менеджер паролей и вставку. Политика должна поддерживать длинные парольные
фразы, проверку распространённых паролей и ограничение максимального ввода; конкретные
лимиты и concurrency/memory budget фиксируются до реализации.

## Предлагаемые операции следующего этапа

Названия ниже описывают операции, не новые готовые endpoint paths. OpenAPI/SDK расширяется
только отдельным совместимым изменением после boundary review.

| Операция                       | Доказательство и результат                                                                                                                                                                             |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Начать enrollment              | Consumer session и recent old-factor reauth для существующего UUID. Нейтральный внешний ответ, rate limit.                                                                                             |
| Подтвердить телефон            | Purpose-bound challenge; доказательство владения без автоматического выбора аккаунта по общему контакту.                                                                                               |
| Указать и подтвердить почту    | Одноразовый email challenge, привязанный к той же попытке; pending email не позволяет login/recovery.                                                                                                  |
| Завершить enrollment с паролем | В одной tenant-транзакции consume proofs, unique/CAS, login binding, password hash и audit для того же UUID. Replay с тем же ключом восстанавливает тот же результат без второй привязки.              |
| Войти по почте и паролю        | Только активный verified login binding; dummy-hash для неизвестной почты, одинаковая ошибка неверных данных, identifier/IP rate limit и bounded hash concurrency. Выдать существующую PadlHub session. |
| Восстановить / сменить пароль  | Только заранее связанный verified метод и одноразовый purpose-bound proof; атомарная смена credential/version, отзыв прежних sessions и audit.                                                         |
| Отключить метод                | Recent old-factor reauth, version/CAS, audit; нельзя удалить последний пригодный способ входа без независимого recovery.                                                                               |

После enrollment нового LOCAL метода отзыв других refresh families и уведомление через ранее
подтверждённый канал входят в завершение команды. Уведомления требуют durable outbox и
проверяемой доставки; отказ доставки не должен повторно привязать метод или создать UUID.

Текущий access middleware проверяет JWT claims/signature, а немедленный отзыв старых access
JWT при password reset ещё не доказан. Следующий этап обязан добавить авторитетную проверку
session/credential generation или эквивалентный механизм: refresh revocation сама по себе
не делает уже выпущенный access JWT недействительным. Reset и concurrent refresh не должны
восстанавливать прежнюю family. Consumer reset не выдаёт staff/admin права.

## Приёмка перед включением

1. Yandex -> phone/email/password enrollment -> LOCAL login возвращает тот же UUID и историю;
   concurrent/replayed completion не создаёт вторую привязку. Unauthenticated регистрация
   отсутствует; Yandex-пользователь без связанных phone/email не получает второй UUID.
2. Отклоняются чужой tenant/user/session, stale old-factor reauth, неверный purpose, истёкший
   или повторный proof, shared contact и identifier другого UUID; конфликт не объединяет записи.
3. Неизвестная почта, неверный пароль и recovery start не раскрывают существование аккаунта.
   Проверены rate limits, password hash memory/concurrency budget и redaction.
4. После reset прежние access/refresh credentials сразу отвергаются; refresh race, отключённый
   пользователь и попытка удалить последний метод не обходят policy.
5. Проверены PostgreSQL non-owner tenant isolation, forward migration/reapply, совместимость
   старых клиентов, audit/outbox atomicity, rollback отключением нового enrollment/login без
   удаления пользователей, credentials или существующих Viva mappings.
6. Пройдены negative tests, полный applicable gate и независимый security/migration review.
   LOCAL, CI, STAGING, PROVIDER и PRODUCTION подтверждаются отдельно.

Для независимости от VIVA ещё нужны подтверждённые phone/email delivery contracts и владельцы
доставки/abuse policy. До их проверки нельзя включать свою регистрацию, recovery или tenant
LOCAL binding. Реальные OTP, provider writes, migration и rollout — отдельные операции.
