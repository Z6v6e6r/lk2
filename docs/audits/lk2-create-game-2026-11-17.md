## 1. Краткий вердикт

Создание игры с оплатой **частично реализовано и не готово к релизу**.

- **Вариант «организатор платит подпиской за свою четверть» реализован сквозным образом**:
  публичный API `/game-create-operations`, идемпотентный журнал, подписанная делегация к LK1,
  prepare → admit → confirm, восстановление после потери ответа, Web-панель, Android/iOS-транспорт,
  CI-проверяемые тесты. Но контур **выключен по умолчанию**, **публичный вход скрыт**, а **живой
  владелец в LK1 не установлен** (последняя зафиксированная проверка — 2026-11-06).
- **Варианты «деньги за свою четверть» и «деньги за весь корт» отсутствуют полностью** — ни
  контракта, ни режима, ни списания, ни UI. `ORGANIZER_PAYS` намеренно отклоняется сервером.
- Второй контур (`POST /games` + advisory WARN из #499/#501) технически живой, но он **не
  бронирует и не списывает**, а оплаченная игра в нём **никогда не становится видимой в каталоге**.
- Шаг «название, диапазон уровней, открытая/приватная» на платном контуре **не выразим в API**:
  владелец LK1 фиксирует 60 минут, 4 места, открытую игру, а `title` отклоняется с `400`.
- Цены в UI **нет вообще**, подтверждения стоимости (`priceConsent`) не формирует ни один экран.

Итог: критерий готовности («организатор создаёт игру с оплатой, LK1/Viva подтверждает операцию, ЛК2
показывает корректную карточку и состав») сегодня достижим **только для подписочной четверти** и
только после внешних действий (установка владельца в LK1, ключи, включение флагов, приёмка на живом
стенде). Для денежных вариантов требуется отдельное продуктовое решение и новый контракт с LK1/Viva.

### 2.2 Второй (устаревающий) контур — advisory WARN

`POST /user/api/v1/:tenantKey/games` с `paymentMode != NO_PAYMENT`
(`apps/api/src/games/game-routes.ts:600-679`) при включённом флаге и транспорте `ADVISORY` создаёт
игру в `PROVISIONING`, операцию в `PENDING` и отвечает `202`/`UNKNOWN` с
`nextAction=WAIT_FOR_RECONCILIATION` (`game-create-commercial.ts`, `game-create-commercial-runtime.ts:146-165`).
Это **наблюдение, а не оплата**: владелец возвращает `SKIPPED_ADVISORY`, брони, списания и квитанции
нет. Публичный `?commercialCreate=1` в Web открывает именно этот контур.

## 6. Что блокирует полноценное создание игр

1. **Владелец quarter CREATE не развёрнут в LK1.** Зафиксированное чтение 2026-11-06: в живом
   Node-RED есть только `booked-operation-*`, маршрутов `/lk/integrations/v1/game-create-*` нет,
   ключи `LK2_BOOKED_OPERATION_DELEGATION_*` не заданы
   (`docs/runbooks/lk2-commercial-acceptance.md:91-98`). Исходники владельца — в репозитории
   `Z6v6e6r/lk`, в этом репозитории их нет.
2. **Ключи и флаги на стенде отсутствуют** — «Absent and blocking»: весь набор
   `GAME_COMMERCIAL_CREATE_*` и `SUBSCRIPTION_RUNTIME_DELEGATION_*`
   (`docs/runbooks/lk2-commercial-acceptance.md:34-39`), конфигурация без них не поднимется
   (`packages/config/src/index.ts:1069-1113`).
3. **Денежных вариантов нет в контракте** — нет режима «деньги за четверть», нет режима «деньги за
   весь корт», нет списания денег, нет квитанции провайдера. Нужно продуктовое решение + новый
   контракт с LK1/Viva.
4. **Шаг 2 не выразим на платном контуре** — `title`, `levelRange`, `visibility` не принимаются
   (`game-quarter-create-routes.test.ts:90-121`), параметры фиксирует владелец.
5. **Оплаченная игра из advisory-контура не публикуется**: `immediateSchedule = paymentMode === 'NO_PAYMENT'`
   (`packages/database/src/game-repository.ts:964`), список и карточка требуют `SCHEDULED`
   (`:1494`, `:1667`, `:1811-1813`), а потребителя `game.provisioning.advance.v1` нет. То есть
   `?commercialCreate=1` — тупик.
6. **Проекция карточки зависит от импортёра LK1**: нужны оба синхронизированных маппинга, точное
   совпадение станции/корта/времени, `capacity=4` и участие организатора
   (`game-quarter-create-repository.ts:649-699`). Иначе `gameProjection` остаётся `PENDING`.
7. **Цена не видна клиенту** — публичный ответ не содержит цены, `priceConsent` нечем заполнить,
   поэтому «подтверждение стоимости» в первом релизе невозможно без аддитивного поля.

Дополнительные риски (не блокеры, но требуют решения):

- Расхождение документации и кода: в двух документах написано, что включение в `production`
  запрещено (`docs/contracts/game-commercial-create.md:3-6`,
  `docs/domain/quarter-create-consumer.md:3`), а проверки `APP_ENV` нет — тест утверждает обратное
  (`packages/config/src/index.test.ts:922-928`). Решение «production разрешён при точном URL
  `https://padlhub.su/`» (`index.ts:1091-1092`) выглядит намеренным, документы устарели; нужно
  зафиксировать одно правило.
- Один `Idempotency-Key` не может назвать JOIN и CREATE: домен `operationId` общий
  (`quarter-create.ts:58`), второй вызов получит `409 GAME_QUARTER_CREATE_KEY_CONFLICT`.
- На приватном wire нет заголовка `Idempotency-Key` (`quarter-create.ts:152-159`), хотя контракт
  требует повтор по `operationId` + ключу.
- Единственный HTTP+PostgreSQL тест advisory-контура (`game-commercial-create-warn-postgres.test.ts`)
  пропускается в CI без `GAME_COMMERCIAL_CREATE_TEST_DATABASE_URL`.
- Локальная особенность: Node 26 + jsdom без `--localstorage-file` ломает storage-зависимые
  Web-тесты (воспроизводится на чистой базе).

## 7. Какие изменения нужны

### 7.1 API (LK2)

1. Новый коммерческий контракт CREATE для денег: режимы `OWN_QUARTER_PAYMENT` и
   `WHOLE_COURT_PAYMENT` + котировка (amount/currency/expiry) + подтверждение цены + квитанция
   провайдера. Переиспользовать существующие `games.operations`, `command_idempotency`, outbox и
   делегацию актора; не создавать второй журнал.
2. Публичная проекция цены для шага 3 (минимум `amountMinor`, `currency`, `expiresAt`,
   `basis`) — иначе подтверждение стоимости не реализуемо. Требует согласия владельца капсулы.
3. `confirm`/`release`/`compensate` для CREATE (сейчас есть только prepare/admit/read) —
   закрывает «частичный сбой» и зависшие dispatched-запросы.
4. Либо потребитель `game.provisioning.advance.v1` (перевод `PROVISIONING → SCHEDULED`), либо
   явное решение вывести advisory-контур из эксплуатации вместе с `POST /games`-оплатой.
5. Расширение тела `/game-create-operations` (`title`, `levelRange`, `visibility`) — только если
   владелец LK1 согласится их принимать и применять.
6. Разделить домен `operationId` по действию (JOIN/CREATE) и добавить `Idempotency-Key` на
   приватный wire.

### 7.2 Интеграция LK1 / Viva

1. Установить владельца quarter CREATE (`nodered_game_create_owner_nodes`) на живой LK1 по
   процедуре репозитория `lk`, включить `LK1_BOOKED_OPERATION_RECEIVER_ENABLED` и
   `BOOKED_OPERATION_EXECUTION_ENABLED`.
2. Спарить делегацию: LK2 генерирует ключ, LK1 доверяет ровно одному ключу. **Риск:** замена ключа
   отрезает другие контуры, которые им пользуются.
3. Реализовать денежный сценарий (своя четверть / весь корт): платёж Viva или иной владелец, квитанция,
   компенсация при частичном сбое.
4. Подтвердить, что бронь корта и списание визита происходят ровно один раз при повторе.

### 7.3 Web и мобильные клиенты

1. Один трёхшаговый экран вместо двух форм: (1) станция/дата/время/корт, (2) название, уровни,
   доступ, (3) способ оплаты, цена, подтверждение, создание.
2. Заменить URL-гейт `?commercialCreate=1` на серверный capability и сделать вход обнаружимым
   (или осознанно оставить скрытым, но задокументировать это как продуктовое решение).
3. Показать цену, срок действия котировки и кнопку подтверждения (`priceConsent`), с обработкой
   `GAME_PRICE_CONFIRMATION_REQUIRED`.
4. Выбор корта: каталог с доступностью вместо «тестовых кортов»; исключить неявное «кортов нет».
5. Состояния ожидания: авто-опрос `nextAction.retryAfterSeconds` с ограничением, единый текст
   «Ожидаем подтверждения», запрет повторной отправки (сейчас — только ручная кнопка).
6. Согласовать навигацию после успеха (сделано в этой ветке: добавлен `revision` в платный переход).
7. Android: оставить только подписочную четверть или явно добавить денежные режимы в allowlist
   транспорта и отдельный экран. Сегодня `POST /games` на Android отклоняется оболочкой.

## 10. Оценка времени и рисков

- **Релиз «только подписка»**: 3–5 рабочих дней **после** внешних апрувов — установка владельца в LK1
  (#1), ключи и включение (#2), приёмка чтением, затем один боевой `--create` (#8).
- **Полный релиз с деньгами**: 4–6 недель двумя параллельными потоками (LK2 #3 и LK1/Viva #4), затем
  Web/UI (#6) и публикация черновиков (#5).

Ключевые риски:

| Риск                                               | Влияние | Снижение                                                                     |
| -------------------------------------------------- | ------- | ---------------------------------------------------------------------------- |
| Один доверенный ключ в LK1 отрезает другие контуры | высокий | сначала чтение LK1, затем выбор «переиспользовать/заменить», отдельный апрув |
| Реальная бронь и списание визита необратимы        | высокий | один прогон `--create`, ручной откат по runbook, refunds вручную             |
| Карточка не появляется без импортёра LK1           | средний | приёмка с игрой из LK1, таймаут PENDING и явный UI-текст                     |
| Двойная публикация/списание при повторе            | высокий | существующие fence/CAS + тесты на потерю ACK (уже есть)                      |
| Денежный путь без LK1-контракта                    | высокий | не реализовывать половину; сначала контракт и владелец                       |
| Расхождение документов про production              | средний | PR #7                                                                        |
| CI не проверяет advisory PostgreSQL-контур         | средний | добавить переменную БД в CI или убрать контур                                |
